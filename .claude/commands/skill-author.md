---
description: 커스텀 스킬을 인터뷰·초안·검증까지 함께 작성한다 (llmwiki skill new의 워크플로우)
---

커스텀 스킬 하나를 **동작이 검증된 상태로** 만든다. 스켈레톤을 떨어뜨리는 것으로 끝내지 않는다.
`llmwiki skill add`가 결정론 스캐폴딩이라면, 이 워크플로우는 의도를 인터뷰하고 실제 볼트에서 근거
소스를 확인한 뒤, 초안을 쓰고 **실행해 보고** 계약 검사를 통과시키는 것까지 담당한다.

- 계약 정본: `llmwiki skill lint`가 검사하는 항목 (`llmwiki --help`의 "SKILL.md 계약" 절)
- 라우팅·신호: `WIKI-CLI.md § 라우팅 결정 절차`, `§ 커스텀 스킬`
- 볼트 워크플로우는 대상 볼트 `CLAUDE.md`가 정본 — 스킬 안에서 재기술하지 않고 위임한다

**쓰기 위치**: 스킬 원본은 사용자 설정 디렉터리다. 반드시 `llmwiki skill path <name>`이 알려주는
경로에 쓴다. 워크스페이스의 `.claude/skills/`는 매 실행 덮어써지는 사본이므로 거기에 쓰면 사라진다.

입력: $ARGUMENTS (스킬 이름, 또는 "주간 회고 만들어줘" 같은 자유 요청, 또는 비움)

## 1. 인터뷰 — 무엇을 자동화할지 좁힌다

$ARGUMENTS로 이미 답이 나온 항목은 다시 묻지 않고, 남은 것만 묻는다. **추측하지 않는다.**

1. **반복 작업이 무엇인지.** 지난번에 이 작업을 손으로 어떻게 했는지 한 번 말해 달라고 한다.
   구체적인 사례 하나가 추상적인 설명보다 스킬 품질을 크게 좌우한다.
2. **트리거 발화.** 사용자가 실제로 어떻게 말할지 2–3개 받는다 (`description`에 인용으로 들어간다).
3. **입력과 출력.** 무엇을 받아서 무엇을 내놓는지. 출력 형태(채팅 전용 / 파일링 / 붙여넣기용 평문).
4. **경계.** 이 스킬이 **하지 않을** 일을 명시한다 (예: 원격 반영, 브라우저 조작, 커밋).
5. **쓰기 여부.** 기본은 read-only다. 볼트에 파일링한다면 어느 디렉터리에 어떤 조건일 때인지.

이름은 마지막에 정한다. 소문자·숫자·`-`만 쓰고, 내장 명령
(`wiki-add`/`wiki-search`/`wiki-use`/`wiki-lint`/`skill-author`)과 겹치면 안 된다.
이미 있는 이름이면(`llmwiki skill list`) 덮어쓸지 다른 이름으로 갈지 묻는다.

## 2. 근거 소스 실사 — 볼트에 실제로 있는지 확인한다

**이 단계를 건너뛰면 안 된다.** 존재하지 않는 페이지를 가리키는 스킬은 lint를 통과해도 실행 시 실패한다.

1. `wikis.local.md`로 볼트 목록을 읽고, 라우팅 절차로 이 스킬의 기본 대상 볼트를 해소한다.
   신호가 애매하면 사용자에게 묻는다.
2. 대상 볼트의 `index.md`를 읽어 필요한 근거가 실제로 있는지 확인한다. 부족하면 `wiki/**`의
   frontmatter·헤딩을 read-only `grep`으로 찾는다.
3. 결과를 사용자에게 보고한다:
   - 찾은 소스는 **경로가 아니라 유형으로** 기술할지 결정한다. 볼트마다 파일명이 다르므로
     스킬에는 유형·태그·패턴으로 적고, 구체 경로는 예시로만 남긴다(다른 머신·볼트에서도 동작).
   - 근거가 아예 없으면 그대로 말한다. 스킬을 쓰기 전에 `wiki-add`로 자료를 먼저 넣어야 하는
     상황일 수 있다. 이때 없는 소스를 가정한 스킬을 쓰지 않는다.

## 3. 초안 작성

`llmwiki skill path <name>` 아래에 `SKILL.md`를 쓴다. 디렉터리가 없으면
`llmwiki skill add <name> --description "<설명>" --no-edit`로 먼저 만들고 내용을 덮어쓴다.

계약이 요구하는 구조:

```markdown
---
name: <디렉터리 이름과 동일>
description: <무엇을 하는지 + 트리거 발화 인용 + 하지 않는 것. 한두 문장.>
---

# <제목>

무엇을 하고 무엇은 하지 않는지 한 단락. 대상 볼트는 `WIKI-CLI.md`의 라우팅 절차로 해소한다.

## 입력
## 근거 소스
## 워크플로우
## 주의
```

작성 원칙:

- **`description`이 유일한 발견 표면이다.** 에이전트는 이 한 줄로 스킬을 쓸지 판단한다.
  1단계에서 받은 트리거 발화를 인용으로 넣는다.
- **볼트 워크플로우를 복제하지 않는다.** 파일링·커밋은 대상 볼트 `CLAUDE.md`의 해당 워크플로우
  (Ingest / Query Filing / Lint)로 위임한다.
- **머신 의존 절대 경로 금지.** 볼트 경로는 레지스트리로 해소한다. 예시로 보여줄 필요가 있으면
  코드블록에 넣는다 — 계약 검사는 코드블록을 판정에서 제외한다.
- **스켈레톤 표기를 남기지 않는다.** 줄머리 `TODO:`·`FIXME:`가 남아 있으면 `error`다. 단, TODO
  정리가 이 스킬의 *주제*라면 본문에서 자유롭게 언급해도 된다(검사는 표기 형태만 본다).
- 여러 변형이 있는 작업이면 **디스패처 절**을 두고, 모호할 때 임의로 고르지 말고 묻게 한다.
- 익명화·비공개 규칙이 필요한 스킬이면 출력 직전 검토하는 **게이트 스텝**을 워크플로우에 넣는다.

## 4. 검증 — 여기까지 해야 끝이다

### 4a. 계약 검사

```bash
llmwiki skill lint <name>
```

`error`가 하나라도 남아 있으면 고치고 다시 돌린다. `warn`은 각각 판단해서 고치거나, 왜 남기는지
사용자에게 말한다. 이 명령이 깨끗해질 때까지 4b로 넘어가지 않는다.

### 4b. Dry-run — 실제로 되는지 실행해 본다

**계약 검사는 형식만 본다. 동작은 실행해 봐야 안다.**

1. 1단계에서 받은 구체 사례를 입력으로 삼아, 방금 쓴 `SKILL.md`의 워크플로우를 **그대로 따라
   실행**한다. 기억이나 추론으로 대신하지 않고 적힌 스텝대로 근거 파일을 읽는다.
2. 이때 다음을 관찰한다:
   - 근거 소스 절이 가리키는 것을 실제로 찾을 수 있는가? 못 찾으면 2단계로 돌아간다.
   - 워크플로우에 판단이 막히는 빈틈이 있는가? (물어야 할 것이 명시되지 않았는가)
   - 출력이 사용자가 1단계에서 기대한 형태인가?
3. **파일링·커밋·원격 반영은 하지 않는다.** dry-run은 read-only다. 스킬이 쓰기를 포함하더라도
   여기서는 "무엇을 어디에 쓸 것인지"만 보고한다.
4. 산출물을 사용자에게 보여주고 확인을 받는다. 빈틈이 나오면 `SKILL.md`를 고치고 4a부터 다시 돈다.

### 4c. 마무리

1. 최종 `SKILL.md` 경로와 `llmwiki skill lint` 결과를 요약한다.
2. dry-run에서 확인된 것과 **확인하지 못한 것**을 구분해 말한다(예: 쓰기 경로는 미검증).
3. 호출 방법을 안내한다: 다음 실행부터 Claude `/<name>`, Codex `<name>`.
   워크스페이스 동기화는 다음 `llmwiki` 실행 때 일어난다.

## 주의

- 사용자가 답하지 않은 항목을 가정해 스킬을 완성하지 않는다. 인터뷰가 이 워크플로우의 본체다.
- 볼트에 없는 근거를 전제한 스킬을 쓰지 않는다. 2단계 실사 결과를 그대로 보고한다.
- 워크스페이스의 `.claude/skills/`·`SKILLS.md`·`.claude/commands/`를 직접 고치지 않는다.
  전부 `llmwiki`가 매 실행 재생성한다.
- 4b를 생략하고 "완성됐다"고 보고하지 않는다. 검증하지 않았으면 검증하지 않았다고 말한다.
